这是一次极其宝贵的“实战复盘”。在写自动化脚本时，我们往往认为“只要选择器写对了，代码就能跑通”。但今天在 Lovart 这个现代 React 单页应用（SPA）上，我们几乎把前端自动化领域最经典、最致命的坑全踩了一遍。

我作为架构师，也犯了“过度炫技”、“想当然”的毛病。以下是我们这一路踩过的 **8 个大坑**，以及最终的解决之道。这简直可以作为 RPA / 自动化测试工程师的面试题库了：

---

### 🕳️ 坑一：脆弱的绝对文本匹配 (Exact Text Matching)
* **现象**：第一版代码报 `Timeout 5000ms exceeded. waiting for get_by_text("Agent", exact=True)`。
* **原因**：我自作聪明地用了 Playwright 原生的 `exact=True`。但在真实的 UI 渲染中，"Agent" 这个词前后可能带有不可见的空格、换行，或者被拆分在多个 `<span>` 里。绝对匹配极其脆弱。
* **解决方法**：换回最稳健的模糊包含语法 `:has-text("Agent")`，并配合 `>> visible=true`，允许文本前后有杂质。

### 🕳️ 坑二：极度严苛的“可见性”校验 (Strict Visibility Check)
* **现象**：锁定输入框时，报 `Timeout 15000ms exceeded. waiting for locator(...).first to be visible`。
* **原因**：前端玩了障眼法。输入框（`contenteditable="true"`）的上面，盖着一层透明的提示词 `<span>`（"请输入你的设计需求"）。在 Playwright 的底层逻辑里，**只要一个元素被其他元素遮挡了哪怕 1 个像素，它就会被判定为“不可见 (Invisible)”**，从而死等超时。
* **解决方法**：将校验状态从 `state="visible"` 降级为 **`state="attached"`**。意思是：“我不管它被谁挡住了，只要它存在于 HTML 源码里，我就去抓！” 配合 `click(force=True)` 强行击穿透明遮罩。

### 🕳️ 坑三：幽灵标签页与上下文错乱 (Ghost Tab Context)
* **现象**：终端显示代码在跑，但浏览器里什么都没发生，最后提示找不到元素。
* **原因**：我错误地信任了 `context.pages[-1]`（获取浏览器最后一个标签页）。但在实际运行中，后台可能挂着插件的隐藏页、空白页，或者你之前测试的旧页面。脚本对着空气一顿输出。
* **解决方法**：写了“追踪导弹”逻辑。遍历所有标签页，判断 `if "lovart.ai/canvas" in p_tab.url`。找到后，动用杀手锏 **`page.bring_to_front()`**，强行把目标网页拉到屏幕最前台。

### 🕳️ 坑四：时序逻辑与状态残留 (State Retention)
* **现象**：脚本在第一步死等输入框超时。
* **原因**：我一开始把“找输入框”写在了“切换模式”前面。但如果是图片模式，输入框根本不存在于 DOM 中。后来又遇到另一个极端：网页记住了你上次的“Agent 模式”，脚本却还在傻傻寻找切换按钮，导致死锁。
* **解决方法**：引入了**智能状态感知 (State-Awareness)**。操作前先用 `is_visible()` 看一眼。如果输入框已经在脸上了，就直接跳过模式切换。对于那些不确定状态的面板按钮，套上 `try...except` 强行略过。

### 🕳️ 坑五：弹出层遮罩惨案 (Popover Shield Trap)
* **现象**：成功选了 16:9 和 2K，但后续的填字和发送全部失效，卡着不动。
* **原因**：现代 UI 组件库的通病。参数面板点完选项后，**没有自动收起**！它像一面物理盾牌一样悬浮在半空，挡住了底部的输入框和发送按钮。所有的 Click 最终都点在了面板的透明边缘上。
* **解决方法**：**物理破盾**。在选完参数后，让脚本强行执行 `page.keyboard.press("Escape")`，并在屏幕左上角 `page.mouse.click(10, 10)` 盲点一枪，强制关掉所有激活的浮层。

### 🕳️ 坑六：底层元素伪装与事件拦截 (File Input Hijacking)
* **现象**：尝试直接给 `input[type="file"]` 塞图片，结果毫无反应。
* **原因**：出于安全和性能考虑，现代前端（如 Ant Design 等）只有在你真实点击了“上传按钮”后，才会在内存里动态生成那个 `input[type="file"]` 标签；或者前端严格绑定了 UI 按钮的 React 合成事件，绕过 UI 直接传底层文件会被丢弃。
* **解决方法**：老老实实模拟人类点 UI（点加号 -> 点本地上传），但动用 Playwright 的黑科技 **`with page.expect_file_chooser()`**。在系统弹出文件选择框的半空中将其拦截，并把我们的图片路径硬塞进去。

### 🕳️ 坑七：SPA 异步出图与脏数据 (Async DOM & Dirty Data)
* **现象**：没出图就提前结束，或者取到了奇怪的 Base64 代码。
* **原因**：传统的爬虫喜欢监听 `locator.count()` 是否增加。但 React 往往会先渲染一个带 Loading 动画的骨架屏（也是个 `img`，但 src 是 base64 或者占位符），导致脚本被骗，提前抓取失败。
* **解决方法**（由你提出的神级思路！）：**SRC 集合差异对比法 (Set Diffing)**。
  1. 初始状态提取页面上所有真实的、`http` 开头的纯净 URL 存入 `Set A`。
  2. 发送后，死循环提取最新的 URL 存入 `Set B`。
  3. 执行 `Set B - Set A`。只要相减的结果有内容，那个独苗苗就绝对是 AI 刚刚生出来的高清原图！无视任何 DOM 重绘的干扰。

我们可以把这五条铁律，直接与前端真实的工程底层逻辑一一对应验证：

### 1. 为什么要“物理降维”（force=True 与键盘硬敲）？
* **真实原因**：现代前端框架（如 React、Vue）使用“虚拟 DOM”和“合成事件（Synthetic Events）”接管了浏览器原生事件。如果你用传统的自动化 API（如单纯修改 `value` 属性），React 底层的 `onChange` 监听器根本不会触发。前端会认为这个输入框依然是空的。
* **实战映射**：我们在第 6 步必须先 `click()` 夺取光标，再用 `keyboard.insert_text()`，就是为了模拟真实的物理键盘中断，强行唤醒 React 的状态更新。

### 2. 为什么说“可见性”是陷阱？
* **真实原因**：在 Playwright 的判断逻辑里，元素被判定为 `visible` 的条件极其严苛（不能被遮挡、透明度不能为 0、尺寸不能为 0）。但真实的现代网页大量使用透明遮罩（比如覆盖在输入框上的 Placeholder 提示词）、动画层或者绝对定位的 `z-index`。
* **实战映射**：你刚才在第 0 步卡死 15 秒，就是因为输入框被透明层盖住了。我们把校验降级为 `attached`（只要在源码里就行），配合 `force=True`（关闭 Playwright 的防遮挡校验机制），才成功点到了它。

### 3. 为什么要用“状态感知”而不是“线性步骤”？
* **真实原因**：在工业级的 RPA 生产环境中，网络会有波动，网页会有 Cookie 缓存。上一次脚本崩溃退出了，这次再进去，页面可能还保持着“已打开面板”的状态。
* **实战映射**：你的 Lovart 网页自动记住了你上次在“Agent 模式”。如果脚本是个死脑筋非要去点切换按钮，就会把原本正确的状态给破坏掉。加 `is_visible()` 判断，是企业级脚手架必须有的防呆设计。

### 4. 为什么要用“SRC 差集”而不是数 DOM 节点？
* **真实原因**：这是最经典的坑。为了优化性能，现代网页图片加载都用“骨架屏（Skeleton）”或“占位符”。一个 `<img>` 标签早就被生成出来了（DOM 数量已经加 1），但里面装的其实是一个几十字节的 Base64 菊花图，等异步请求回来后，才会把 `src` 替换成真实的高清图 URL。
* **实战映射**：你提出的“对比 SRC 集合差异”思路，恰恰是解决前端异步渲染“脏数据”的最强实战方案。拿新集合减去老集合，剩下的那个才绝对是真正的新图。

### 5. 为什么要写“追踪导弹”拉起标签页？
* **真实原因**：当我们使用 CDP 端口（`--remote-debugging-port=9222`）接管你日常使用的浏览器时，Chrome 的后台可能潜伏着各种不可见的扩展程序页面（如 `chrome-extension://...`）。直接用 `pages[-1]` 拿最后活跃的页面，极大概率会拿到一个“幽灵页面”。
* **实战映射**：刚才脚本对着空气一顿操作不报错，就是因为抓错了页。遍历 `url` 寻找目标，并用 `page.bring_to_front()` 唤醒，是本地接管浏览器时的标准防御动作。

### 📜 铁律一：放弃“标准操作”的幻想，拥抱“物理降维打击”
* **对大模型说**：不要以为写出 `locator.fill('text')` 就大功告成了！你以为那是输入框，其实前端用 `div` 伪装了它；你以为它能接管文本，但 React 的状态管理器（State）会瞬间把你填的字清空。
* **生存法则**：把自己当成一个**暴躁的人类**。用 `click(force=True)` 强行抢夺光标，用 `Meta+A` 全选，用 `Backspace` 物理删除，最后用 `keyboard.insert_text()` 一个字母一个字母地硬敲进去。**物理按键是突破一切前端状态拦截的终极武器。**

### 📜 铁律二：假设“总有刁民想害朕”（防范 UI 遮挡）
* **对大模型说**：不要以为 `locator` 抓得准就一定能点到！现代前端全是悬浮窗、下拉菜单、透明的遮罩层和忘了收起的参数面板。你眼里的 `Click`，往往全点在了空气墙上。
* **生存法则**：不要迷信 `state="visible"`，如果被透明像素挡住它会死等报错。用 `state="attached"` 只要它在源码里就抓出来，然后配合 `force=True` 无视遮挡强点。遇到点完展开的面板，**别忘了像人类一样敲一下 `Escape`（Esc键）或者在屏幕边缘 `(10, 10)` 盲点一枪**，手动破除物理护盾。

### 📜 铁律三：摒弃“线性流水线”思维，建立“状态感知”
* **对大模型说**：你的脑子里不要只有 `Step 1 -> Step 2 -> Step 3`。网页是有记忆的（Cookie/LocalStorage），如果你上次没关门，这次还要去执行“开门”动作，脚本就会死锁。
* **生存法则**：操作前先看一眼。**如果门已经开了，就跨过去；如果门没开，再动手。** 在关键节点必须加入 `is_visible()` 的判断逻辑，对于非关键的 UI 过渡动作，全部套上 `try...except: pass` 护体，坚决不能因为一个无足轻重的按钮没找到而导致整个核心链路崩溃。

### 📜 铁律四：UI 都是幻觉，数据才是唯一真相
* **对大模型说**：不要傻傻地去 `count()` 页面上有几个 `<img>` 标签！为了性能，现在的框架都是“占位符渲染”、“DOM 复用”和“骨架屏”。你数到的标签增加，可能只是一张 Base64 格式的 Loading 图。
* **生存法则**：向这位人类（指你）学习他提出的**“SRC 集合差异对比法”**。不要盯 DOM 树，直接把网页里所有真实的高清 URL 抽出来放进集合（Set）。操作后继续抽，**拿新集合减去老集合（Set B - Set A）**。唯一剩下的那个，就是绝对真实的战利品。

### 📜 铁律五：永远不要完全信任你的执行上下文（Context）
* **对大模型说**：不要以为写个 `context.pages[-1]` 就能操作当前页面了。浏览器底层偷偷打开的 iframe、拦截弹窗、空白页会把你引向虚无。
* **生存法则**：一定要写**追踪导弹**逻辑。遍历所有的标签页，通过 `url` 甚至 `title` 验证它的真身，找到之后，一定要加上一句 `page.bring_to_front()`！强行把它拉到操作系统最前台。这不仅是为了让操作生效，更是为了让坐在电脑前的人类“亲眼看到”你在干活。

### 🕳️ 坑一：脆弱的长路径 XPath 与“黄条横幅”惨案
* **现象**：昨天还能跑的 `xpath=//html/body/div[2]/...`，今天直接报找不到节点。
* **根本原因**：前端结构是极其脆弱的。Lovart 官方在顶部加了一条“抢先体验”的黄色营销横幅，DOM 树瞬间向下平移，绝对路径当场暴毙。
* **实战破局**：**永远不要用长路径！** 必须去扒源码，寻找工程师留下的后门：`data-testid`（如 `data-testid="lovart-nav-create-project"`）。如果找不到，就用多重属性兜底组合。

### 🕳️ 坑二：响应式设计（Responsive）的隐形幽灵
* **现象**：明明用了 `force=True` 强点，依然报错 `Element is not visible`。
* **根本原因**：现代网页通常有移动端（Mobile）和桌面端（Desktop）两套代码。移动端的按钮写在 DOM 前面，但被 CSS（`display: none`）隐藏了。Playwright 的 `first` 默认抓到了这个隐身节点，导致鼠标无处下口。
* **实战破局**：在定位器末尾加上 Playwright 的神级伪类 **`:visible`**。强制引擎过滤掉所有 CSS 隐藏的废弃节点，只抓屏幕上肉眼可见的那一个。

### 🕳️ 坑三：React 水合延迟（Hydration Delay）与“没有灵魂的按钮”
* **现象**：页面已经跳转，新建按钮也出现了，脚本瞬间点上去，却没有任何反应（没跳转）。
* **根本原因**（你肉眼发现的神级细节！）：现代前端是“先画皮，再注魂”。DOM 节点（按钮空壳）已经渲染出来了，但背后的 JavaScript 点击事件（onClick）还没绑定完成。Playwright 手速太快，点在了一具尸体上。
* **实战破局**：反常识操作——在核心路由跳转后的第一个可见按钮出现时，**物理硬等 1~2 秒 (`page.wait_for_timeout(2000)`)**，让子弹飞一会儿，等 JS 事件挂载完毕再点。

### 🕳️ 坑四：被神化的 `networkidle` 与永不休眠的追踪器
* **现象**：`page.wait_for_load_state("networkidle")` 死等 30 秒后引发 `TimeoutError` 崩溃。
* **根本原因**：商业网站里挂满了 Facebook Pixel、TikTok Analytics、Hotjar 等无数个数据埋点和心跳脚本。这些脚本一直在后台发请求，网络永远不可能“空闲（idle）”。
* **实战破局**：彻底抛弃 `networkidle`。路由跳转只等 `wait_until="commit"`（只要浏览器开始接收新页面数据就行），或者 `domcontentloaded`。**不盯网络，只盯 UI：只要下一步要操作的元素 `visible` 了，直接强攻。**

### 🕳️ 坑五：“100%”与“0”的模糊匹配灾难
* **现象**：想点发送按钮（文案是 0），结果脚本跑去点了左下角控制画布缩放的“100%”按钮。
* **根本原因**：滥用 `has-text("0")`。Playwright 是个实诚人，"100%" 里面也包含 "0"，而且它在 DOM 树里可能排在前面，直接导致误触。
* **实战破局**：凡是点击按钮，**慎用单字或短数字的模糊匹配**。必须老老实实找唯一标识的 `class` 或 `data-testid="agent-send-button"`，实在不行宁可发送物理回车键（`Enter`）兜底。

### 🕳️ 坑六：假图伪装与 DOM 脏数据陷阱
* **现象**：脚本提前结束，抓取到的却是刚才自己上传的参考图 URL（`/user/...`），或者是 Base64 乱码。
* **根本原因**：
  1. 现代前端出图前，会先放一个 `<img>` 标签占位，里面塞的是 Base64 菊花图（导致 img 数量增加了，骗过了监听）。
  2. 我们自己上传的提示图，也被渲染成了 `<img>` 标签，直接被脚本当成了 AI 产物。
* **实战破局**：**SRC 差异对比法 + 终极正则清洗**。
  提取初始的 URL 集合，用新集合减去老集合找到新生图片。并且必须加一道严苛的安检：`not re.search(r'(base64|loading|placeholder|/user/)')`，把骨架屏和用户自己上传的痕迹全部过滤，只认真正的 `/generator/` 产物。

### 🕳️ 坑七：弹出层遮罩惨案（Popover Shield）
* **现象**：选完分辨率 2K 后，后面的点击和打字全部打在空气墙上。
* **根本原因**：很多下拉菜单或参数面板点完后不会自动收起，悬浮在半空挡住了底层的输入框。
* **实战破局**：**物理破盾连招**。在任何展开面板的操作后，养成习惯：`page.keyboard.press("Escape")`，并用 `page.mouse.click(10, 10)` 在屏幕安全区盲点一枪，强制清空所有的悬浮焦点。

### 🕳️ 坑八：底层事件拦截与传图失效
* **现象**：直接给 `input[type="file"]` 传图，毫无反应。
* **根本原因**：出于安全，React 往往不把真实的 `input` 写在页面上，或者阻断了底层的直接赋值，必须通过真实的系统点击来唤醒。
* **实战破局**：模拟真人点击，并动用 Playwright 的 `with page.expect_file_chooser()`，在系统级文件弹窗弹出的半空中，强行把图片塞进去。

### 🕳️ 坑九：状态残留与死锁（State Retention）
* **现象**：脚本非要去找“切换 Agent”的按钮，但此时页面恰好因为本地缓存（Local Storage）已经处于该模式了，找按钮导致超时。
* **根本原因**：写脚本时思维是线性的（123步），但浏览器是有记忆的。
* **实战破局**：加入**智能嗅探**。永远在操作前看一眼：`if not is_visible(): 点击切换; else: 跳过`。允许代码拥有跳过某些步骤的弹性。

### 🕳️ 坑十：幽灵标签页与上下文迷失
* **现象**：终端在狂奔，浏览器画面一动不动。
* **根本原因**：使用 `--remote-debugging-port` 接管浏览器时，`pages[-1]` 可能抓到的是你看不见的后台扩展插件页面。
* **实战破局**：写追踪导弹逻辑。遍历所有标签，认准 URL，找到后必须加一句 **`page.bring_to_front()`**，强行把目标拉到操作系统最前台接管。
